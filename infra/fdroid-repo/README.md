# infra/fdroid-repo

Phase 6 (`CLAUDE.md` §5): "Stand up the F-Droid repo (or
Obtainium-compatible feed) for distributing 'App' (MCP integration)
packages." `build-repo-demo.sh` builds and verifies this for real,
reran clean twice.

## What's real

- A genuine signing keystore, generated by the actual F-Droid tooling
  (`fdroidserver init`, real 4096-bit RSA in a PKCS12 keystore), not a
  hand-rolled substitute.
- Real tarballs of the hub's actual MCP apps — `hub/apps/file-search/`,
  `hub/apps/notes/`, `hub/apps/smart-home/` — packaged from their real
  source, not placeholders.
- A real integrity check: each package's sha256 is computed from the
  actual tarball bytes and cross-checked against what the index
  records.
- A real cryptographic signature over the index, via `jarsigner` — the
  same signing primitive F-Droid's own `index-v1.jar` uses.
- A real negative control: tampering with the *signed* jar's content
  (not a never-signed copy — see "what was fixed" below) and
  confirming `jarsigner -verify` correctly detects and rejects it.

## What's NOT real, and why

This is not a spec-compliant F-Droid or Obtainium index. Both formats
are built around distributing signed Android APKs; the hub's "Apps"
are Python MCP servers, not Android packages. There is no way to make
that honestly spec-compliant without lying about what the packages
are — an index claiming APK entries for tarballs would be a false
claim, not a scope simplification.

Building an actual placeholder APK to satisfy the format was tried and
abandoned. `aapt2 link` / `aapt package` need `android.jar` to resolve
any `android:` manifest attribute — even trivial ones like
`versionCode` or `label`. No `android.jar` is available: apt's
`android-sdk` package on Ubuntu 24.04 ships build-tools and
platform-tools only, not a platform, and `dl.google.com` (where the
platform normally comes from) is blocked by this environment's network
policy — the same restriction documented in `pocket/client/README.md`
for the same reason. Confirmed by directly running
`aapt package -M AndroidManifest.xml`, which failed with nine distinct
"No resource identifier found for attribute" errors (versionCode,
versionName, minSdkVersion, targetSdkVersion, label, hasCode, name x2,
exported) — verified, not assumed.

So: real signing infrastructure, real packages, a real signature —
over this project's own custom, clearly-labeled index format, not a
fabricated claim of fitting a format built for something these
packages aren't.

## What was fixed after the first pass

The negative-control check originally tampered with a copy of the
plain, never-signed `index.json`, zipped it, and asked whether
`jarsigner -verify` rejected it. That's a different and weaker claim
than intended — it only shows jarsigner can tell an unsigned jar isn't
signed, not that tampering with real signed content is detected. The
corrected version copies the already-signed `index.jar`, modifies the
`index.json` entry inside that same jar (leaving its `META-INF`
signature entries untouched), and confirms `jarsigner -verify` now
fails on the mismatch between the signed manifest and the altered
content.

## Running it

```sh
apt install fdroidserver default-jdk-headless
./build-repo-demo.sh
```

No root required. Uses `python3.12 -m fdroidserver` directly rather
than the `fdroid` CLI wrapper — on this system the wrapper script
defaults to python3.11, which hits a PIL native-extension mismatch
(apt's PIL `.so` files are built for cpython-312) and fails with an
`_imaging` ImportError before it does anything real.
